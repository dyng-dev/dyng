**Located.** Three causes, separated by the stage reading
(`parity/experiments/sssp_stage_ab.py`), the parts of the tool's own report
(`$DYNG_SCRATCH/runs/m11b-step1/tools/e2e_parts_ab.py`: the read, canonicalize, apply and SOSP
times it prints, and every profiler stage), both sides rebuilt with R020's flag set FB
(`-falign-functions=64 -falign-loops=32 -Wa,-mbranches-within-32B-boundaries`, the JCC-erratum
mitigation) and a scan of the branches the JCC erratum affects
(`$DYNG_SCRATCH/runs/m11b-step1/tools/jcc_scan.py`; records `M11b-d13-location-*.json`):

1. **sosp_update +2.5-3.5 % was the code: the push iteration's per-edge loop.** The stage reading
   (rgg safe50k, 21 rounds) put it in `sssp.loop` (+3.5 %; identify_affected 0.99-1.00, seed
   0.99-1.00, finalize 1.00), and so did the parts on rgg (loop 1.043, everything else of the
   update within 1 %). **With FB on both sides it stayed** (sosp_update 1.016-1.032 on roadNet-CA
   and rgg; loop 1.038 in the parts). In the object, the per-edge loop of `loop()._omp_fn.1`
   differed from the parent's: with the element passed by value to the noinline cold path, GCC 12
   kept it in a register and spilled the vertex the relaxation reads instead (a stack load per
   relaxed edge where the parent stored the element). Passing it by reference, as `push_back` and
   its `_M_realloc_insert` do, restores the parent's instructions and registers in that loop:
   `8e2f3df` (v2).
2. **end_to_end +4-6 % is code placement in the graph reader**, code the fix did not change (its
   objects are byte-identical): in the parts (rgg), `read graph` +53 ms (1.106) was the whole
   end-to-end difference (+54 ms), and with FB it was 0.994 (end_to_end 0.996); the FB readings
   put end_to_end at 0.996-1.004 on every graph. The libdyng.so functions after the engine's
   object moved (8,998 of 11,628 text symbols changed their address mod 64).
3. **The JCC erratum also hit the push loop in v1:** the scan finds the macro-fused `cmp`/`jge`
   that closes the per-edge loop of v1's `loop()._omp_fn.1` (int32) across a 32-byte boundary,
   which the parent's loop does not have; FB builds have no affected branch in the engine.

### 2.3 The shared engine (ADR 0095 decisions 1, 3-7)

`engine::operators` on cuda runs sssp's operators kernels over hyper_sssp's `line_graph_view`
(the slack_csr store's line graph: slack rows `rowStart[v] .. rowStart[v] + deg[v]`, node weights
`w[col]` pushing and `w[v]` pulling, one symmetric view as `in` and `out`, the public mode's base
offers, the work counter) with the host loop of sssp's operators engine. hyper_sssp's own kernels
turn the store's record into `sssp_changes`: a deleted pair (a, b) -> the changes a -> b and
b -> a; a new, recreated or dead id v -> (parent[v] -> v), a root whatever its parent, never the
virtual source row; a node of the public mode that lost the source (parent -1) -> (-1 -> v), a
root exactly when its parent is -1; the inserted pairs and the gained nodes are relaxed after the
pull. The budget is MOSP_ESCHER's triggers where they apply (HD8, ADR 0092): before each push
round, iterations >= max_iterations, then relaxations > work_budget x max(1, live entries), in
MOSP_ESCHER's units (the row lengths of the invalidated nodes' pulls and of the pushed nodes);
sssp's packing replaces the 32-bit width (`distance_width` where n x the largest weight does not
fit) and a pointer jumping that does not end in ceil(log2 n) + 1 rounds is `invalidation_depth`.
`invalidate_subtree` and `packed_min` now have two users but stay in `algorithms/sssp/` (moving
them renames every sssp and mosp kernel; ADR 0095 decision 7; a rename-only follow-up in
`docs/roadmap.md`). The internal knobs' defaults (warp rows, unbounded update width, pair seeds,
the shared static solve) were chosen on informal GPU-1 timings, each variant replayed by id on T
and P first (`$DYNG_SCRATCH/runs/m11b-step2/replays/`, 0 mismatches each).

### 2.9 The decision (HD13)

The rule (decided by the author on 2026-10-28): the shared engine becomes `engine::automatic`'s
choice only if it is byte-identical to the as-is engine and to B (it is: section 2.4) **and**
within every gate (it is not: 4 `sosp_update` rows of section 2.6, 1.051-1.061 against 1.05).
**`engine::automatic` keeps `engine::fused`**; `engine::operators` stays selectable with the same
results; the reason and the numbers are on the algorithm page (`docs/algorithms/hyper_sssp.md`
section 5). The static recompute: the shared static solve does not read slower (0.69-0.74 of the
ported recompute), and each engine keeps its own (the rule chooses an engine whole; an as-is
update with the shared static solve is a follow-up after 0.4.0 in `docs/roadmap.md`, ADR 0095
decision 8). No code changes for the decision: `engine::automatic` already maps to
`engine::fused` (`hyper_sssp.cpp`), and `<dyng/hyper_sssp.hpp>` documents it. A shared-engine
gate miss is not a STOP; sssp's and mosp's objects are identical (section 2.2), so S7 does not
arise. For the PR description: "O12: the shared sssp engine gives MOSP_ESCHER's results bit for
bit but is 5-6 % slower than MOSP_ESCHER in four coauth-DBLP update rows (bar 5 %), so by HD13 the
as-is kernels stay the default; `engine::operators` is selectable."
