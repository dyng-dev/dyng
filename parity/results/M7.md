Run-to-run spreads of this engine A/B (fused against operators, the same program; not the gate
records of section 6, whose spreads and PLAN 8.6 flags are listed there): 0-4 % on every
per-objective region. The end-to-end runs differ by 0.1-3.7 % (the engine is a small part of a
run that reads text files and applies the batch on the host).

Reading. The operators engine runs the fused engine's algorithm phase by phase (the round counts
above are the operators engine's; the fused one's are of the same size), so the difference is the cost of
leaving the GPU between rounds: one host round trip per near-far round, about 8-9 us each on
this machine (roadNet-PA local10k: 5.8 ms more over 644 rounds; road_usa local10k: 9.4 ms over
1186 rounds), plus the launch latency of the per-round kernels. Where an update has many short
rounds (the local batches, the small road graphs) the engine is 1.4-1.6x the fused one; where
rounds carry much work (rgg, the road_usa 50K batches) 1.03-1.09x. A later step could keep the
near-far loop on the device for several rounds between synchronizations (or capture the rounds
in a CUDA graph) if the fallback's speed ever matters. The risk that `docs/developer/plan.md`
lists for 0.2.0 ("the operators engine within 1.05x of the fused one", in its "Main risk" column)
materialised on the local batches (1.4-1.6x); no gate applies (M7 acceptance criterion 1 makes
the comparison informational).

## 7. The combined step ("watch", PLAN 6.4.4)

PLAN 6.4.4 asks to watch the combined step, where MP2 once regressed 40 % through a
non-aggregated atomic. dynG's count pass sums the edge count and the weight sum per warp before
its two atomics (as MOSP-CUDA's), and the OpenMP pass uses relaxed atomics as MOSP-OpenMP's.
Reported ratios of the combined step (`combined` region: Steps 2-3 against the originals'
`combined_graph_gpu` / `combined_graph_compute`):

| backend | roadNet-PA | roadNet-CA | rgg | road_usa |
|---|---|---|---|---|
| cuda | 1.003-1.039 | 0.996-1.007 | 1.003-1.016 | 1.000-1.034 |
| openmp | 0.611-0.627 | 0.674-0.715 | 0.583-0.611 | 0.546-0.632 |

On OpenMP dynG's combined step is 0.55-0.72x of the original's. On cuda it is 1.00-1.04x: on
roadNet-PA's 50K batches 2.58 ms against 2.48 ms (before section 8's fix 2.63 ms, the separate
`affected` kernel included), on road_usa's 59.5 ms against 57.5 ms. The kernels are not slower:
Nsight Systems on GPU 1 (default clocks, road_usa, the 50K safe batch, one update) gives
dynG's count / scan / fill / solve 6.21 / 0.28 / 2.87 / 48.12 ms against MOSP-CUDA's
6.98 / 0.28 / 2.80 / 48.23 ms, the same gaps between them, and host region times of 58.0 ms
(dynG) and 58.8 ms (MOSP-CUDA) in that run. The 0-4 % of the locked-clock A/B is therefore host
time around the same kernels, not a kernel regression, and the gated "(a) compute" region that
contains the step is 0.996-1.005x. Not gated on its own (PLAN 8.6 gates the paper-timed regions;
it would be within 1.05x even so).

**The OpenMP comparison is not like for like** (M7 review). MOSP-OpenMP@c352151's `mospUpdate()`
declares a fresh local `CombineWorkspace` (`src/mospUpdate.cpp`), so the first use inside its
timed `combined_graph_compute` stage allocates, zero-fills and first-touches the combined CSR
(`cursor.assign(n + 1)`, `rowPtr.resize`, `colInd` / `weights.resize(edges)`,
`src/combinedGraphCpu.cpp:170-192`). dynG's `mosp_workspace` comes from the handle's pool and its
`reserve()` returns at once when the capacities exist: the arrays were sized and touched by
`mosp::result::from_arrays()` in the setup, outside region "(a)". Part of OpenMP's 0.55-0.72x is
therefore the pooled workspace (ADR 0015), not the combine and the solve themselves: on roadNet-CA
the review measured 23.97 / 16.16 ms (safe50k) and 34.52 / 24.92 ms (local10k); the original's
first touch of about 64 MB (K n = 5.9 M edges, 4-byte ids and weights, plus two (n + 1) offset
arrays) is of the order of that 8-10 ms difference (an estimate, not a measurement). A
cold-workspace reading of dynG's step (a fresh pool before the update) was not taken: it needs a
new mode of `dyng-compat-mosp` and is not gated (docs/developer/retrospectives/M7.md, open items).
The CUDA comparison is symmetric: both sides reserve their device workspace before the region.

## 8. Device memory (PLAN 8.6: <= 1.05x)

`parity/perf_ab.py memory --mosp --gpu 0 --graph <g>` (new in this step: the port runs

reading of M3): each side once per batch under `nsys profile --cuda-memory-usage=true`, the peak
of its live device allocations (cudaMalloc and cudaMallocAsync, memory kind Device).

**The first reading missed the gate**: 1.068-1.075x of MOSP-CUDA's peak on the three road graphs
(roadNet-PA 252.3 against 236.3 MiB, roadNet-CA 454.7 against 425.2 MiB, road_usa 5,232.8
against 4,867.9 MiB; rgg 0.951x; records `M7-mosp-memory-before-cuda-<graph>.json`). The excess
was the second pair of combined arrays that the cuda result kept for `affected` (12 bytes per
vertex: the solve wrote the spare pair while the previous MOSP tree stayed for the count kernel;
road_usa: 274 MiB).

**Fix** (`5e20e0f`, ADR 0027 amendment): the combined solve overwrites the previous MOSP tree in
place and the engines count the changed vertices in their unpack pass, as an update counts its

`count_changes` parameter instead of `!from_scratch`, which an update always sets, so the
per-objective updates run the same code path; its register counts stay 59 / 60 / 64; the
operators engine runs its counted unpack). The count kernel, its synchronization and the spare
arrays are gone (an update with path costs synchronizes K + 3 times with the fused engine, C8).
The host backends keep their spare pair (host memory has no gate).

## 11. The packing window (M7 review; ADR 0029, proposed)

The review found that inside the packing window (n - 1) * W <= max_distance < n * W the host
backends (MOSP-OpenMP's rule) run distance-only and the CUDA engines (MOSP-CUDA's rule) run
packed, so non-canonical imported trees give different parents on the two groups (ADR 0029;
`docs/algorithms/sssp.md` section 4). Per-backend parity in the window, checked once against the
unpatched `bin/mosp` of both originals (`$DYNG_SCRATCH/ref/<repo>@<sha>/unpatched`) with the
review's generator (`$DYNG_SCRATCH/runs/m7fix-window/window.py`: a graph of n vertices with
3 n edges of weights 1-3 (K = 2) plus one edge of weight W that is never on a shortest path, the
Dijkstra trees of `mospPrep init` with 70 % of the tie parents replaced by other tight
in-neighbours, 3000 deletions and 2000 insertions, Pref {2, 3}), against `dyng-compat-mosp
--mosp` of the parity and parity-cuda presets on the library code of `d3a5f47`. Compared files:
`obj{0,1}/{distances,SSSPTree}Updated.txt` and `combinedGraph/{distancesCsr,SSSPTreeCsr,
mospCosts}.txt` (7 files):

| case | n | W | trees | sequential, OpenMP (8) | cuda fused, cuda operators | MOSP-OpenMP vs MOSP-CUDA |
|---|---:|---:|---|---|---|---|
| win65537_lo | 65537 | 2147450881 | non-canonical | = MOSP-OpenMP (7/7), 5 files differ from MOSP-CUDA | = MOSP-CUDA (7/7), 5 files differ from MOSP-OpenMP | 5 files differ (2146 lines of obj0's tree); distances equal |
| win65537_hi | 65537 | 2147483647 | non-canonical | = MOSP-OpenMP | = MOSP-CUDA | 5 files differ (1504 lines of obj0's tree) |
| pack_lo (the review's case) | 65538 | 2147450879 | non-canonical | = MOSP-OpenMP | = MOSP-CUDA | 5 files differ (2214 lines of obj0's tree) |
| win65537_canon | 65537 | 2147450881 | canonical (as `mospPrep init`) | = MOSP-OpenMP | = MOSP-OpenMP | equal (7/7) |

`stats::packed_parents` is 0 on the host backends and 1 on cuda in every window case. So each
backend is byte-identical to its own original on every input, and the backends differ only for
non-canonical trees in the window, as ADR 0029 option A states; the hand test
`SsspPackingWindow.NonCanonicalTreesFollowEachOriginalsPackingRule` pins the same behaviour in
the unit suites. The rule itself (keep each original's, or one rule everywhere) waits for the
author (GOVERNANCE.md, open decisions).
