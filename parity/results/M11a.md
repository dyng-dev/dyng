HD2. Parity rule for B's virtual rows and public-mode parents (parity rule).
- Default by_id:
  - the harness loads B's {s} and {t} rows as ordinary hyperedges at B's positions (container weight 1; dynG id = B id - 1; the M8b precedent);
  - an INTERNAL virtual-endpoint mode of hyper_sssp (no public name) seeds B's source row at distance 0 and weighs both rows 0 in hyper_sssp's own copy;
  - distances and parents are then compared with B's exactly, by id.
- by_id_public: distances equal on every real hyperedge; parents may differ only where B's parent is its source row (dynG: -1) or its virtual target row. Each such case is counted and checked against dynG's oracle.
- by_key on a user-loaded container: distances by (sorted vertex set, weight); parents as dynG's canonical tree.
- Coverage:
  - cuda: T + all 16 P;
  - sequential: T + dblp_{hyperedge,vertex}_50000 + geology_hyperedge_50000;
  - openmp: container-level only.
- Why: B's zero-weight target is a node of its line graph, and after batches its id is below reused ids, so it wins ties as the canonical parent. No public source-vertex API can reproduce that by id; distances are unaffected.

HD3. Gate rows (measurement protocol).
- Default, gated per batch b1..b3:
  - maintain = t_delta + t_csr_apply <-> the whole hypergraph.apply (conservative: dynG's scope also holds the id assignment B times in t_escher);
  - sosp_update;
  - static (a recompute into a second result, no rebuild);
  - dynamic_comparable = t_delta + t_csr_apply + t_sosp_update <-> the whole update;
  - dynamic = t_dynamic_total_ms (PLAN 6.4.8's figure, flagged in the improvement table).
- Gated end to end: load_plus_dynamic at 1.10.
- Bars: 1.05 where B's median is at least 10 ms, else 1.10 with at least 21 rounds.
- Reported only: escher, delta and csr_apply separately (csr_apply is 1.5-28 ms on host timers, and its scope is not one-to-one), load, wall, an improvement table.
- No h2h-CBST mode for parity.
- Why: B's total is 50-71 % CBST maintenance that nothing on the SSSP path reads and that slack_csr does not have. Gating only the total would let that improvement mask a regression (PLAN 8.6).
- Alternatives: gate delta and csr_apply separately; or gate only the dynamic total.

HD7. Fallback decisions and the frozen fallback_used doc (parity rule + a stable field).
- Default: the per-batch fallback decision is not a parity target (PLAN 8.3 does not list it).
  - On the as-is engine's gate rounds it is a per-round guard: a differing round is repeated, and a configuration differing in more than a third of its rounds is reported as 'scope differs'.
  - For the shared engine it is tabulated beside B's.
- The frozen update_stats doc (core/stats.hpp:36-38) labels fallback_used 'Deterministic', while B's CUDA work count depends on scheduling near the threshold (Geology hyperedge 100K/200K fall back about 5-7 % over the limit in the 07bbceb data, identically in all three runs; a flip near the limit is possible in principle but was not observed).
  - Default (joint with M10's AD20): a documentation-only api-change to core/stats.hpp lets an algorithm state a weaker level for an inherited field, per field. The sentence is written once: M10a step 3 owns it, and M11a step 4 writes the identical sentence if M10a has not merged ('An algorithm's stats documentation may state a weaker level (deterministic per backend, or schedule-dependent) for an inherited field; that statement governs for that algorithm.'). hyper_sssp's stats docs then state that fallback_used is deterministic on sequential, and schedule-dependent on cuda near the budget: a batch within a few percent of it may fall back in one run and not another, with identical results.
  - Alternative: make the device work count schedule-independent (a different unit from B's) or count only at deterministic points.

HD8. Budget semantics and option names (parity rule + naming).
- Default:
  - the as-is engine keeps B's triggers exactly: work > work_budget x max(1, live entries) checked before each push round; 4096 push rounds; 64 jump rounds; the 32-bit packed overflow;
  - public: double work_budget = 1.0 (B's multiplier; 0 = recompute after any work; +inf = none), std::int64_t max_iterations = 4096, budget_action on_budget = recompute | error, plus cuda_engine and validate_inputs;
  - stats gains relaxations and a fallback_reason enum;
  - on_budget governs only the work and iteration triggers; the packing overflow and the jump cap always recompute.
- Alternative: the sketch's int64 'frontier visits, 0 = automatic', with an internal override for the compat path.

HD9. Incidence-edit scope and the storage matrix (behaviour on stable surfaces).
- Default:
  - incidence edits on slack_csr storage on every backend; escher storage keeps not_supported_error in 0.4 (documented, strong guarantee, the message naming slack_csr);
  - slack_csr storage takes line_graph none, automatic (maintained as slack_csr) or slack_csr, and requires store_v2h;
  - escher + slack_csr and slack_csr + sorted_merge are refused;
  - triad_count refuses slack_csr storage (strong guarantee), so hyper_sssp and triad_count cannot share a hypergraph in 0.4;
  - line_graph_view.overlaps stays empty; h2h() builds a sorted view on request;
  - no new public capacity_policy fields (B's slack rules are internal knobs selected by mosp_escher(extra)).
- Why: escher h2v rows must stay sorted (ADR 0042), and this leaves the gated 0.3 paths untouched.
- Alternative: incidence edits on escher storage with re-sorted rows plus an incidence-aware sorted_merge, in a later release.

HD10. .dgb incidence edits (a stable format).
- Default: hypergraph-file flag bit 3, 'incidence_edits', after bits 0-2 (deleted_members, expected_ids, insert_first).
  - Two counts and the removal/addition arrays per record.
  - Flags are fixed at open: whole-file writers set the bit only if some batch needs it, and batch_writer takes it at construction and rejects a batch that needs it otherwise. So edit-free files stay byte-identical.
  - 0.3 readers already reject unknown bits with io_error.
  - .dgt +i/-i stays at format version 1 (its syntax was reserved in PLAN 5.7).
- Why: flags compose, and a 'version 2' could clash with M10's own .dgb additions.
- Joint decision with M10's AD13: bit 4 vertex_records and weight code 3 = float32 for graph files; one ADR section per milestone.
- Alternative: format version 2, coordinated with M10.

HD11. Distance semantics and the weight limit (API).
- Default:
  - distance_to(v) = min over live h containing v of D(h), following the sketch. PLAN 5.3's '+ w(h)' double-counts, because B's D(h) already includes w(h) (HostHypergraph.cpp:386; Oracle.cpp:124);

  - vertex_distances() computed on request, not maintained per update (sketch open question 1);
  - weights in [1, 2^28] validated by hyper_sssp (strong guarantee); the container keeps [1, 2^31 - 1].
