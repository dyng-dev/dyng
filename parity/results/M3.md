# M3 parity and performance record: the framework migration

Date: 2026-09-29. M3 moves `sssp` and `cycle_count` onto the framework layer
(`cpp/src/framework`, PLAN Sections 4.5.1-4.5.5) one commit at a time (PLAN Section 6.3 step 8).
After every commit the golden parity is re-run, and a commit that touches a gated hot path gets a
performance spot check. This file is the log of those checks. The final gate suites of the
milestone (acceptance criterion 3) are recorded in their own section when they are run.

### 1.4 End to end on OpenMP: code alignment in the CSR reader, not the update

The dynG-against-dynG reading of commit 3 shows every timed update stage equal or faster, but
`total.end_to_end` of `dyng-compat-mosp` 25-35 ms (5-8 %) slower. The whole difference is in
reading the graph (`read_csr_triplet`, the text parser of the input CSR: 215-241 ms before,
252-257 ms after), which this step does not touch; every profiler stage of the update, the
graph build and the result imports is equal or faster (a stage-by-stage A/B of both builds,
7 rounds).

The cause is code placement. The sssp objects precede the I/O objects in `libdyng.so`, so the
larger sssp code moves the CSR parser by 0x44d0 bytes (16 bytes modulo 64). The Xeon Gold 6258R
is a Cascade Lake part, whose microcode mitigation of the jump-conditional-code erratum slows
branches that cross or end on a 32-byte boundary, so a hot loop can gain or lose several percent
from such a shift. The proof: both builds rebuilt with `-Wa,-mbranches-within-32B-boundaries`
(the assembler pads branches away from those boundaries) read the graph in the same time
(199-217 ms before, 199-203 ms after, alternating, 5 rounds each). A build with only the new
sssp files on top of `f664f96` (the rest of the tree unchanged) reproduces the slower read.

The `parity-cuda` build of the same code places the reader differently again: there the migrated
code reads end to end 1.6-2.3 % faster than `f664f96` (commit 4). So the end-to-end ratio moves
with the layout of unrelated code, not with the migration; the gated
update regions (sosp_update per objective, apply) are unchanged. The end-to-end gate against the
original holds with a wide margin (0.72-0.82x in section 1.2). The final gate suites of M3 read end
to end again on the final code.

## 2. `cycle_count` onto the enactors (step migrate-cycle)

The pre-migration code is `b8c3794` (the end of section 1; its `cycle_count` code is that of
`019ef13` apart from the empty budget-counter calls of `099a73d`). Its `dyng-compat-cycle-enum`
was built from a `git archive` copy under `$DYNG_SCRATCH/m3-cycle/base` (`parity` and
`parity-cuda` presets) and is the "before" side of the spot checks.

`cycle_count` is the aggregate-delta problem `cycle_count_problem` (`algorithms/cycle_count/
problem.hpp`, members in `cycle_count.cpp`): `ownership_type = ownership::min_member` (I2),
`normalize` (`cycle_count.normalize`), `count` on the old view (`cycle_count.count_minus`, the
subtraction on G_t), `identify_affected`, `count` on the new view (`cycle_count.count_plus`),
`finalize` (the signed delta, `internal_error` for a negative bucket), and for `compute()` `reset`
-> `count` (`cycle_count.count`) -> `finalize`. The lifecycle members carry the M2 participant's
checks (the stale-result check through `framework::expect_current_result`, the same messages).

### 2.1 Protocol of the checks

- **Parity (every commit).** `parity/compare.py cycle_count --full` on the `parity` preset (the

  72 replays) and `parity/compare.py cycle_count --set cycle_count_cuda --configs

### 2.4 OpenMP GitHub update on the final code: code placement, not the migration

The dynG-against-dynG reading of the final code (21 rounds, 56 threads) has every gated region
within 2 % of `b8c3794` except the GitHub 25K+25K update: **1.036x** (129.2 -> 133.8 ms; 41
rounds: 1.029x). After commit 2 the same case read 0.998x. A stage-by-stage A/B (15 rounds)
puts the difference in the two phases (`cycle_count.count_minus` 1.029x, `cycle_count.count_plus`
1.051x), which call the unchanged OpenMP engine (`openmp.cpp`, `cycle_count_openmp_phase`) with
the same arguments, and in unrelated code: `graph.build` (the CSR build before the prior count,
not touched by M3) reads 1.205x. The CUDA commit made `cycle_count.cpp` larger (the Tier B
members), which moves the code linked after it in `libdyng.so`.

The same test as in section 1.4: both trees rebuilt with `-Wa,-mbranches-within-32B-boundaries`
(the assembler pads branches away from the 32-byte boundaries of the Cascade Lake
jump-conditional-code erratum): **update 0.999x** (120.7 / 120.6 ms), `graph.build` 1.002x,
`count_minus` 1.009x, `count_plus` 1.010x (15 rounds, alternating). So the difference moves with
the layout of the library, not with the migration; with the padding both builds are 7 % faster
than either build without it, which says the parity preset's flags leave the host engines
exposed to this erratum. The gate against the original holds with a wide margin (update 0.44-0.56x
in commit 2). Changing the parity preset's flags would change the measurement protocol of
ADRs 0018/0021 (an author-approved rule), so it is not done here; the final gate step of M3 reads
this case again against `019ef13` and records it with this explanation.

## 3. The conformance kit and the contributor tooling (step kit-scaffold)

This step adds the conformance kit (C0-C12, `cpp/tests/conformance`), the algorithm registry,

0022, `docs/developer/conformance.md`). Most of it is tests and tools; the library changes are:

| Change | Where | Hot path? |
|---|---|---|

| Check | Finding | Resolution |
|---|---|---|

The reviewers' reading (section 4.2 was wrong to call the local10k medians noise) was repeated
and taken apart with `parity/experiments/sssp_stage_ab.py`: the two builds run alternately with an
idle parent (no machine monitor, output discarded), and every gated stage is compared per
objective and per mode. Records in `parity/results/M3-review-diag/` (the review's intermediate
builds) and `M3-review-quiet-*.json` (the final build).

1. **The difference is in the near-far loop, not in the enactor.** The gated region is the sum of
   the hooks `sssp.identify_affected`, `sssp.seed`, `sssp.loop` and `sssp.finalize`; the enactor's
   own code runs between them. On the final build with the idle parent: rgg local10k reads
   1.077-1.091 with `sssp.loop` 1.090-1.103 and the other stages 0.98-1.04 (0.2-4.6 ms of them);
   roadNet-CA local10k reads 0.981-1.006; roadNet-PA safe50k 1.010-1.022 (the loop 1.016-1.028).
   The loop's source is unchanged since `019ef13` (the M3 migrations moved it into
   `sssp_openmp_engine::loop()` verbatim, plus an early return for an empty graph).
2. **It predates the sssp migration.** `f664f96` (the framework added, sssp not yet migrated,
   the OpenMP engine's source untouched) is already 1.061-1.079 of `019ef13` on rgg local10k, with
   the loop 1.077-1.078; the OpenMP migration itself (`95ec7a0` against `f664f96`) reads
   0.986-0.994 (`bisect-*.json`).
3. **It moves with the placement of code.** Built with every function aligned to 64 bytes
   (`-falign-functions=64`, both builds), the final code reads 1.006-1.012 of `019ef13` on rgg
   local10k (the loop 1.006-1.009, mode by mode 1.001-1.009, with the same share of slow-mode
   rounds, 7 / 8 of 25) and 0.984-1.001 on roadNet-CA local10k (`align-*.json`); the cycle_count
   CUDA DD update reads 1.005 (3.743 against 3.764 ms; without alignment 1.021, the difference in
   the host stage `cycle_count.normalize`, 1.071, whose code M3 did not change). The Cascade Lake
   core of this machine is sensitive to where branches fall (sections 1.4, 2.4, 3.3: the
   jump-conditional-code erratum), and adding any code to `libdyng.so` moves the hot functions.
4. **The two modes are not the harness and not the address space.** They persist with ASLR off
   (`setarch -R`, both builds: 6 / 12 slow rounds of 21 on roadNet-CA objective 2) and with
   transparent huge pages off (`PR_SET_THP_DISABLE`: every stage slower, the modes still there,
   6 / 8 of 21); with the idle parent roadNet-CA local10k is unimodal for both builds, rgg is
   bimodal for the unaligned final build only, and with aligned functions both builds show the
   same mix. The mode frequency, like the loop's time, is a property of the layout of the binary.
5. **`list_gather`'s inline offsets** (the kit step, `12cc6b9`) are one of the layout changes:
   with the `019ef13` version of the header the unaligned final build read 1.030-1.042 on rgg
   instead of 1.07-1.09. `ed03afb` aligns the inline array to a cache line (the threads' writes no
   longer share a line with the members every thread reads); no effect on the time could be
   separated from placement.

**Conclusion.** On this machine and in the parity preset, the final code is 1.01-1.10x of
`019ef13` on the short OpenMP sssp batches (worst: rgg local10k with an idle parent, 1.08-1.09x),
1.02x on roadNet-PA safe50k objective 2 and 1.01-1.03x on cycle_count's CUDA DD updates; with
the functions of both builds aligned the same way, every one of these is within 1.2 %. The
update's work is unchanged; its speed on the Xeon Gold 6258R depends on where the linker puts the
hot functions, which any change to the library moves. Criterion 3's 2 % bar against the pre-M3
code is therefore **not met as measured** for these regions, and meeting it by controlling the
layout (a function-alignment flag in the parity and release presets, a per-algorithm flag of PLAN
8.6) is a protocol decision that is not delegated: it is recorded for the author
(`GOVERNANCE.md`, open decisions; the retrospective, open item 1). Every gate against the
unpatched originals holds with a wide margin (section 5.3: OpenMP sssp 0.63-1.00x).
