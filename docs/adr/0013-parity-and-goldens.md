# ADR 0013: Parity and goldens

- **Status:** Proposed (draft, M1a); accepted with the 0.1 release, after the CUDA port (M1b) and
  `cycle_count` (M2) have used it
- **Date:** 2026-09-27
- **Deciders:** S M Shovan (lead maintainer)

## Context

Every algorithm of dynG is a port of a research repository, and the promise of the library is
that a port computes exactly what the original computes (PLAN Sections 6.3 and 8.3). That promise
is only worth something if the evidence can be reproduced later, by someone else, on a clean
machine: the originals keep changing on their own branches, local tags do not travel, scratch
directories of a session disappear, and results that exist only in CI logs are lost (risk R22).
The originals also must not be touched: they are the authors' research artifacts, and a build
inside them (or a stray patch) would change the thing that is being compared against.

M1a is the first use: `sssp` on the CPU against MOSP-OpenMP@c352151, plus the one-off cross-check
of MOSP-CUDA@e220ee2 against MOSP-OpenMP.

## Decision

1. **Pinned references.** `parity/references.toml` lists each original with its full commit SHA,
   the SHA of its local `baseline-2026-09` tag, its location, upstream remote, build command, run
   environment, smoke test, gitlinks, external inputs and toolchain. The port must match the
   pinned commit; the baseline SHA documents what the papers measured.
2. **Scratch builds only.** `parity/build_reference.sh` exports the pinned commit with
   `git archive` into the persistent work area `$DYNG_SCRATCH/ref/<name>@<commit7>/` (never a
   session temporary directory, never the repository), in two variants:
   - `unpatched`: the archive as is; **performance baselines come only from it**;
   - `patched`: the archive plus **additive** export tools (`parity/export_patches/<repo>/`,
     sources in `parity/exporters/`); no original file is modified. Goldens come from it.
   The script verifies that every tracked file of a copy still equals the archive (content, type,
   executable bit), that the original repository's HEAD and status are unchanged after the build,
   and writes the archive-build check (gitlinks left out, local-only inputs, absolute paths,
   external inputs). It is idempotent.
3. **Goldens outside the repository, manifest inside.** `parity/export_goldens.py` writes the
   golden sets to `$DYNG_SCRATCH/goldens/<set>/` (for `sssp`: 388 cases, 144 MB) using only the
   original's own tools and test programs to create inputs. Each set has a `MANIFEST.sha256` of
   every file; the committed `parity/goldens.toml` records the manifest's SHA-256 and one digest
   per case. Small cases stay committed as test fixtures under `cpp/tests/data` (< 1 MB in
   total). Paper-scale inputs (roadNet-CA etc.) are regenerated by the original's `mospPrep` and
   recorded by the SHA-256 of every input file in the performance record. The release-asset path
   of PLAN Section 8.3 (`goldens-vN.tar.zst`, `fetch_goldens.py`) is added when CI needs the
   goldens (M4).
4. **Cross-check the originals first.** Before a golden is written, every original
   implementation that computes the same thing must agree byte for byte (for MOSP-OpenMP:
   `mosp`, `parallelSOSPUpdate`, `sequentialSOSPUpdate`, `mospPrep expected`); where two original
   repositories compute the same thing (MOSP-CUDA vs MOSP-OpenMP) they are compared once on the
   whole corpus before any port is blamed for a difference.
5. **Exact comparison.** `parity/compare.py` first re-verifies the goldens against the manifest,
   then replays every case through the drop-in driver (`tools/compat`) on every backend and
   thread count and compares bytes. The tolerance rules are those of PLAN Section 8.3 (none for
   `sssp`, `mosp`, `cycle_count`, `triad_count`, `hyper_sssp`; calibrated only for
   `label_propagation`). Comparisons are never loosened to make a port pass. CTest runs the
   replay under the label `parity` (skipped when the goldens are absent).
6. **Honesty checks.** Goldens are exported twice from two fresh archive copies and must have the
   same manifest; a recorded mutation must make the replay fail; a changed golden byte must be
   detected.
7. **Performance records.** `parity/perf_ab.py` alternates the unpatched original and the port
   (A/B/A/B, median of at least 5 runs, under `$DYNG_SCRATCH/perf.lock`, 28 threads pinned for
   OpenMP) on the regions defined by `parity/timed_regions/<algo>.toml`, written before the port.
   It also checks once per batch that both write identical outputs.
8. **The parity certificate is committed.** Each milestone writes `parity/results/<milestone>.md`
   with the JSON records next to it (reference and port commits, toolchains, presets, the golden
   manifest SHA-256, the case x backend matrix, tolerances, the performance table). From the
   first release, `parity/certify.py` writes `benchmarks/results/<version>/parity.json` in the
   same format (PLAN Section 10.3).

## Consequences

- Parity evidence can be regenerated from three inputs: the original repository at the pinned
  SHA, the dynG commit, and `$DYNG_SCRATCH` (or a fresh one: every artifact in it is rebuilt by
  the scripts, except the prepared dataset CSR files, which come from the SuiteSparse downloads
  and are identified by their SHA-256 in the performance record).
- The work area needs space (M1a: 26 MB + 30 MB of reference copies, 144 MB of goldens, 160 MB
  of benchmark inputs); the repository stays small (the manifest is 52 KB).
- An export patch that is not purely additive, or a golden that needs a patched timing path, is
  a change of this ADR and must be recorded.
- Until the goldens are published as a release asset (M4), the `parity` CTest label is run on
  the author's machine only; CI runs the committed fixture subset.
