## Deviations and decisions (each with the same intent)

1. **The CHANGELOG section was renamed**, not followed by a new `[0.1.0]` section: nothing in
   the library changed since 0.1.0rc1, so a separate section would only list the version and
   the documents. The renamed section keeps the record of 0.1.0rc1 and adds a "Final release
   (R011)" entry; the link reference `[0.1.0rc1]` is dropped with its heading (the tag
   `v0.1.0rc1` stays, and the summary names it).
2. **The order of the checks.** The `packaging` and `tests` checks ran at `261d03d` (the
   version and the status texts), before this retrospective and the developer plan's status
   line, which are outside their scopes; the `repo` checks (`ci/check.sh --parity`,
   `ci/gpu_local.sh`) ran after the last change outside `benchmarks/results/`, so this
   retrospective names their results by reference to the certificate. The mutation CTests ran
   in the `ci/gpu_local.sh` clone (the same `dev-cuda` build) rather than in the sanitizer
   clone.
3. **Step 8 on one machine.** The smoke test was run on the GPU machine (the CPU wheel's host
   backends); no separate CPU-only machine is available to this milestone. The wheel has no
   CUDA backend, so the two runs test the same code; the hosted CI's sdist and wheel jobs cover
   other machines.
4. **A retrospective of its own** (R011) instead of a fourth step of R010, since the final
   release is its own milestone.

## The review round

Independent reviewers (release-manager lens) confirmed five findings; each is fixed here:

| Finding | Fix |
|---|---|
| The README's Status table still said the Python package was "to be published with 0.1.0" | the row in the released state: on PyPI since 0.1.0 (`pip install dyng`); CUDA plugin wheels follow in 0.1.x |
| The orchestrator note said a release-date fix re-records only `distributions`; `CHANGELOG.md` and `CITATION.cff` are also in the `repo` scope (`parity.json`, `code_paths.repo` is the whole tree but `benchmarks/results`), so `check-parity` and `gpu_local` would go stale too | the note corrected (below): a date change re-runs and re-records `distributions`, `check-parity` and `gpu_local`, then `certify.py write` again |
| The orchestrator note let O3 and the licence expression's objection window wait until the author's approval of the `pypi` deployment; `release.md` step 10 requires them before the tag is pushed (pushing `v0.1.0` uploads `NOTICE` and the `License-Expression` to TestPyPI, and neither the tag nor the 0.1.0 file names can be replaced) | the note follows step 10 (below); GOVERNANCE.md's O3 now says "before the tag `v0.1.0` is pushed" |
| The certificate's README, copied from 0.1.0rc1, described the release candidate's check records as if they were this directory's | a sentence at the top of its section "What was run, and how" says those records were replaced by the R011 runs; the two bullets say which statements are the release candidate's |
| `install.md` called 0.0.1 the current PyPI version; `release.md`'s readiness pointer left out R011 | "The PyPI release 0.0.1 was only the name reservation"; the pointer names this retrospective |

**Not done here: moving the release date.** The reviewers suggested setting the CHANGELOG
heading and `date-released` to the realistic tag day in this pull request. That day is not known:
the tag waits for O3, which only the author can settle, and `ci/wheel_check.py --release-date
today` must pass on the day of the tag. So the date stays 2026-10-01 (the day of this pull
request) and the note below says exactly what a later tag day costs.

The licence row of the approvals log (GOVERNANCE.md, 2026-09-30) says the expression stands
"pending objection before the final PyPI approval". It is a log entry and is left as written;
`release.md` step 10 is the binding deadline (the objection window closes before the tag).
