#### Deviations from the plan and the step's text (each with the same intent)

1. **The fix is three library commits, not one** (`e0d6129`, `e80c24c`, `8e2f3df`). `e80c24c`

   left the results readable, against the documented basic guarantee); `8e2f3df` changes how
   `region_push_back()` passes the element after the first ADR 0024 reading located a real cost
   (2-4 % in the push iteration's per-edge loop, also with FB on both sides). Each is its own
   commit; ADR 0094 covers all three, and the readings of record are those of the final library
   (v2); v1's are kept in the record (ADR 0024 rule 4).
2. **The reading's side B is a build of the fix, not of HEAD** (the parity harness of the run
   clone, `perf_ab.py` of `cedabfc`, records `"commit": "cedabfc..."` for the port, the clone's
   commit, not the library's): the record names each side's library by version and sha256
   (`parity/results/M11b.md` section 1.1). No later commit of the step changes the library.
3. **`perf_ab.py mosp --baseline-exe/--baseline-label/--layouts`** is M10a's commit `36e2a7e`
   cherry-picked unchanged (`cedabfc`), as the step's text allows when M10a has not merged ("add
   it to the same spec"); the merge of M10a then brings the identical change.
4. **Location tools outside the repository.** The parts of the tool's report
   (`$DYNG_SCRATCH/runs/m11b-step1/tools/e2e_parts_ab.py`) and the JCC-erratum branch scan
   (`tools/jcc_scan.py`) are experiment scripts of the step's run directory, like the FB compiler
   wrapper of M11a (`m11-builds/fb/g++-fb`); their outputs are in `M11b-d13-location-*.json`.
5. **The first attempt was cut by the account's usage limit** (2026-11-04, 08:15Z); its commits
   and its nohup'd reading driver (`runs/m11b-step1/readings_all.sh`) survived, and the resumed
   attempt let that driver finish (its later jobs measured v2, after the in-place rebuild of the
   reading's head tree; the record dates each window). The resumed attempt also found its own
   check driver terminated after the tsan-openmp run (by a process outside this step; the
   sanitizer had passed and written its log) and ran the corpora in a driver of its own. A second
   attempt was cut the same way at about 18:40Z; its nohup'd drivers (`readings-v2-long.sh`,
   `readings-v2-mosp-long.sh`, `post-v2.sh` with `corpora.sh`, `final-checks.sh`) survived, and
   the third attempt waited for them, checked every exit status and log, and wrote the records.
6. **Twelve small probe compiles ran without the shared lock** (`thread_list_fast_path.py
   probe`, about a second each, at about 09:30Z and 12:54Z); the second batch fell into the window
   `adr0024-mosp-openmp-roadNet-PA` (v1), whose contamination monitor rejected no round (foreign
   load at most 1.04 of 2.0 cores). Compiles of any size now take the shared lock.

7. **Rule 3's re-reads went past the step's round counts**: the 50K batches of sssp and mosp at 85
   layouts x 170 rounds (the step names 17 x 51), local10k at 85 x 340 where 85 x 170 left a
   region outside or an interval over 3 % wide; the readings of record are the longest of each
   region (`parity/results/M11b.md` sections 1.5-1.6).
8. **The shared-lock drivers of the third attempt wait for queued exclusive windows for at most
   15 minutes** (`corpora2.sh`, `final-checks2.sh`): with both tracks queueing their windows back

#### Results

- The fix holds every guarantee: each of the six new tests ended the process on the parent and
  passes on the fix; the sssp (495 cases on sequential, openmp at 1-56 threads, cuda and
  cuda-operators) and mosp corpora are byte-identical; every CUDA object is unchanged (SASS and
  host code); the push fast path is push_back's (GCC 12/13, Clang 18).
- ADR 0024 (HD16): sssp's update stages within the bar after the v1 cost was fixed; end_to_end
  (1.071-1.100), mosp's path_costs and one bimodal mosp local10k stage are above it, located (code
  placement in byte-identical objects, or a mode mix with each mode within) and listed for the
  author (GOVERNANCE.md, Open decisions, M11 (HD)). The PLAN 8.6 gates against
  MOSP-OpenMP@c352151 hold (84 cells; no S7).

#### Lessons

- **A fast path equal to push_back's is not enough: look at the loop around it.** The probe and
  the per-function compare counts were right in v1, and the push loop was still 2-4 % slower,
  because the signature of the cold call changed which values the compiler kept in registers. The
  reading's stage split (identify_affected, seed and finalize unchanged; loop +3.5 %), the FB
  rebuild (the cost stayed) and a diff of the one outlined function found it in an hour; passing
  the element as `push_back` does restored the parent's instructions.
- **Separate code from placement before calling anything placement.** The same v1 reading had
  both: the end_to_end excursion vanished with FB (the graph reader, byte-identical objects at
  other addresses), the loop's did not. Calling both "placement" would have shipped a real cost.
- **One stream of shared-lock work at a time.** Two overlapping shared holders (a check run and a
  build) kept the exclusive windows of both tracks waiting for over an hour; the resumed attempt
  ran its shared work in one sequential driver and its long shared jobs only while no exclusive
  window waited.
- **A driver must hand `tools/locklog.py run` an executable, not a shell function.** The mosp
  driver of the second attempt passed its function `m`; three windows opened and closed at once
  with no reading. A dry `bash -n` and a one-line check that the command resolves (`type -P`)
  before a long queue would have caught it.

#### What was built

**For M10b (the slack-row accessor):** M10b had not merged, so the slack-row view is written once
in `cpp/src/util/slack_rows.cuh` (`detail::slack_rows<vertex_t, offset_t, degree_t>`:
`row_start`, `deg`, `col_ind`, and `begin(v)`, `end(v)`, `neighbour(e)` on the device), read by
hyper_sssp's `graph_access` in the shared engine; M10b's
`row_layout::slack` / `slotted` can read its rows through it (or extend it) instead of a second

#### Deviations from the plan and the step's text (each with the same intent)

1. **The step ran in two attempts.** The orchestrator stopped the first on 2026-11-05 at 13:43Z
   (the author paused the project); its commits, its replays and corpora, the 11-round P50
   reading and ADR 0024's coauth-DBLP reading (window `ab0024-shared-vs-asis-dblp`, which finished
   on its own) are kept: they ran on the same build of the step's final library (a `git archive`
   of `3655ccf`; no later commit changes `cpp/` or `tools/`). The resumed attempt (2026-11-10)
   took the rest in a nohup'd driver (`$DYNG_SCRATCH/runs/m11b-step2/readings2.sh`, log
   `readings2.log`).
2. **The readings are at base clocks although the fresh probes held boost** for their 3 rounds:
   the suite's rule (`ia3_hsosp.yaml`, M11a's `ba1120b`) reads both datasets at base because
   neither held boost through a 21-round reading; the same rule keeps the shared engine's table
   comparable with the as-is engine's.
3. **The records' `commit` is the worktree's HEAD at the time** (`2eb182b`; `3655ccf+dirty` for
   the 11-round reading, whose uncommitted change was the harness's `memory --port-arg`, later
   `e38eb59`), not the library's: section 2.1 names the build.
4. **ADR 0024's 102-round re-reads cover a whole configuration** (both rows, all three batches)
   wherever one row was above 1.02 at 51 rounds, in one window per configuration.
5. **The static solve**: HD13 keeps the ported recompute for static only "if the shared compute
   reads slower"; it reads faster (0.69-0.74), but since the default stays the as-is engine, each
   engine keeps its own static solve. An as-is update with the shared static solve would be a
   third engine the rule does not define; it is a follow-up in `docs/roadmap.md`.
6. **The rule of two** is met by `invalidate_subtree` and `packed_min`, but they stay in
   `algorithms/sssp/`: moving them to `cpp/src/operators/` renames every sssp and mosp kernel
   (their namespace is in the mangled names), which would cost the identity proof of criterion 2.
   A rename-only follow-up after 0.4.0 (`docs/roadmap.md`).
7. **The internal knobs' defaults** (warp rows, unbounded update width, pair seeds, the shared
   static solve) were chosen on informal GPU-1 timings, not in exclusive windows; every variant
   was replayed by id on T and P before it was timed, and the gate reading is of the defaults.
8. **The first attempt's commits had not passed `ci/check.sh`** (its driver was stopped before
   the checks): the records commit `1005b49` failed the provenance check (a Derived-from line
   missing from `hyper_sssp/operators.cuh`) and two release-certificate tests that did not list
   the new mutations. `713b23d` (a comment, after the readings: no instruction changes) and
   `605063d` (the tests) fix them; `ci/check.sh` passes on `605063d`.

#### Results

- sssp and mosp: 51 kernels (20,504 instructions) and every host object identical to step 1's
  library; the sssp corpus 495 / 495 and `mosp_scale` 20 / 20 on cuda and cuda-operators.
- The shared engine: byte-identical to the as-is engine and to MOSP_ESCHER in the three parity
  modes on every batch of T and P (212 M ids by id), update == compute, ten identical runs; the
  fallback decisions equal B's on every batch (75 / 75); the mutation twins detected.
- The gates against MOSP_ESCHER: memory 0.493-0.561 (bar 1.05); static 0.690-0.740 and
  load_plus_dynamic 0.641-0.810; **4 `sosp_update` rows of coauth-DBLP's hyperedge batches above
  1.05** (1.051-1.061; the as-is engine 1.001-1.024). By HD13 the as-is engine stays the default
  and `engine::operators` stays selectable (ADR 0095 decision 8; the algorithm page's section 5).

#### Lessons

- **A bounded loop is not free when the original exits early.** sssp's pointer jumping launches
  its ceil(log2 n) + 1 rounds (each a no-op after convergence) to avoid a synchronization per
  round; MOSP_ESCHER synchronizes and stops. On a road graph the bound is cheap; on a line graph of
  22 M entries the extra launches over n are a measurable part of a 22 ms update. The stage timers
  of the gate reading found it without a new tool.
- **Prove identity before measuring.** Recording the SASS of sssp and mosp before the first
  policy and comparing after each commit made criterion 2 a script run instead of four readings,
  and caught nothing only because each policy was written to inline to today's code.

#### Lessons

- **"Byte-identical text" is the wrong test for a CUDA library.** nvcc's per-compilation unique
  names make two builds of the same source differ in `.rodata` and therefore in every
  rip-relative displacement; compare instruction streams at the same addresses with the
  displacements normalized (and the SASS with the names normalized) instead. A plan that wants an
  identity route for readings should name that comparison.
- **A shared driver should name the executable target it needs.** `dyng_hsosp_replay` is the
  replay library and `dyng_hsosp_replay_tool` the program; a build of the library alone passes,
  and the replays fail at their first stage, which a driver that stops on the first failure
  would have shown at once.
- **Do not commit while `ci/check.sh` runs on the same worktree.** Its harness tests compare the
  commits they record at the start with HEAD at the end, and its scaffold check copies the working
  tree: a commit and an edit made during the run failed both (`checks-check.log`); the steps were
  run again on the final tree.

**Lessons across M11.**

- **Exact parity first, then the shared engine, made the shared engine cheap to judge.** With
  the as-is engine exact by id, the shared engine's parity was one more replay with `--same-as`,
  and its readings a decision rather than an investigation.
- **The reference's own exports are the best oracle input.** Replaying MOSP_ESCHER's exported
  batches (HD5) kept every comparison exact, including its forced overflows and fallbacks.
- **Every reading needs a clean, named build.** The `+dirty` refusals of M11a and the clone of
  this step are the same lesson: a record is only as good as the commit it names.
- **Two tracks need a calendar and anchors, and still conflict in files without anchors.** The
  shared lock-window log kept the readings of M10 and M11 apart; the P040 anchors kept the shared
  code files mergeable; the one code conflict found (`ci/cmake_consumer.sh`) was in a file that
  had none.
