### Deviations from the plan (each with the same intent)

1. **The sssp suite is `ipdps25_dynamosp_sosp.yaml`, not `ipdps25_dynamosp.yaml`.** The DynaMOSP
   papers time the K = 3 per-objective updates plus the combined-graph step (`mosp`, 0.2); 0.1
   ports the per-objective update (`sssp`), which the 0.1 gate compares per objective (PLAN
   6.4.2). A suite named after the paper but timing only part of its pipeline would be
   misleading, so the 0.1 suite carries the `_sosp` suffix and says what it measures; the
   mosp-level suites `ipdps25_dynamosp.yaml` and `tpds25_dynamosp.yaml` come with `mosp`.
2. **The runner is `parity/bench_suite.py` over the A/B harness, not `dyng-bench run`.** PLAN 8.5
   item 2 describes an end-to-end driver through the public API (`tools/bench`, `benchmarks/run.py`);
   the gates of PLAN 8.6 are read by the existing A/B harness through the compat tools, which is
   what a release must certify. The suite format is the one of PLAN 8.5's example (datasets,
   batches with seeds, backends, runs, metrics mapped to profiler stages, baselines,
   tolerances), extended with `readings` (which harness invocation, which clock lock, gated or
   recorded) and validated against the harness. A public-API driver can read the same files later.
3. **No `benchmarks/baselines/<repo>-<commit>.json` files.** The original's medians are in every
   compacted record and in the suite summaries (`original_ms`, `original_mib`), next to the
   hardware and the commit; a separate copy would duplicate them.
4. **The temporal datasets of DynTruCy** (CollegeMsg, email-Eu-core, time-window mode) are listed
   under `deferred` in the suite and not run: the time-window and temporal modes arrive in 0.4.
5. **`parity/mutate.py` covers the sssp mutation only.** The cycle_count mutations of PLAN 8.4
   are CTests since M2a (`ctest -L mutation`, host and CUDA); `mutate.py` adds the one that needs
   the golden corpus (a skipped subtree invalidation, on each backend). The triad, label
   propagation and MOSP_ESCHER mutations come with their ports.

### What happened on the way

- **A busy shared machine during the first pass.** At times between 23:51 on 2026-09-30 and
  01:00 CDT a workload outside the perf lock kept about 27 cores busy. The A/B harness of sssp
  rejected the rounds and, after 12 rejections, stopped two readings (CUDA `road_usa_g` at locked clocks,
  default-clock `roadNet-PA`), as designed; the OpenMP cycle_count harness flags such runs but
  does not repeat them, so its reading completed with almost every run flagged, and the summary
  passed it. `bench_suite.py summarize` now lists flagged runs per case under `contaminated`
  (without failing, PLAN 8.6), and the flagged reading was taken again with the two stopped ones
  and the default-clock cycle_count reading the usage limit had interrupted (README of the
  results, "Readings taken again"). Note for later: the cycle_count OpenMP harness should repeat
  flagged runs like the others (a change to `parity/cycle_count_perf.py`, deliberately not made
  during a release).
- **No re-measurement for the later commits.** The commits after `d13d393` change only harness
  scripts, documents and C++ tests, which the certificate verifies (`git diff` over the library
  paths is empty); a measurement is not repeated for them.
- **Portability pre-check** (the C++ test changes of `dd09893`): the Clang 18 syntax pass over the
  dev build's 161 translation units and the `_FORTIFY_SOURCE=3` cpu-only build are clean.

### Deviations and decisions (each with the same intent)

1. **The certificate accepts a metadata-only library difference with an equivalence record.**
   Making the algorithms stable changes `cpp/src` (the two manifests and the generated registry
   table) after step 1 measured the gates, the replays and the sssp golden mutations at
   `d13d393`; under step 1's rule (the measured commit has the release's library sources) the
   certificate would fail, and measuring the whole gate again would take several hours of the
   exclusive lock that M7 also needs, for a change no measured program executes. Instead,
   `parity/certify.py equivalence` builds `d13d393` and the release's library over it in one
   clone (same paths, same `VERSION`, presets `parity` and `parity-cuda`) and compares the files:
   both compat tools are **byte-identical** and `libdyng.so` differs only inside
   `dyng::algorithms()` (553 bytes of `.text`) plus the build id, unwind and symbol tables, with
   every section and symbol at the same address. The rule is narrow: only the files of
   `METADATA_PATHS`, only the library scope (the gates, the replays, the golden mutations), and
   only with a passed pair whose release side has the release's library. The test-suite checks
   read the registry, so they were **run again** on the release code instead. The rule and the
   record are in `parity.json` (`metadata_paths`, `equivalences`).
2. **The decision date.** The author's decisions were given on 2026-09-30; the approvals log and
   the comments that cite them use that date, while the release date of the CHANGELOG and
   `CITATION.cff` is 2026-10-01.
3. **The sdist carries the wheel's licence expression.** One `[project]` table serves both, so
   the sdist (whose own files are all Apache-2.0) also names the bundled components' licences; a
   broader expression than the sdist needs, never a narrower one (`docs/developer/wheels.md`).
4. **The pre-alpha wording** was replaced in `CONTRIBUTING.md`, `SUPPORT.md` and `SECURITY.md`
   too, not only in the README, so the repository says one thing.
