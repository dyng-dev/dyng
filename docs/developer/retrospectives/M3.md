## Deviations from the plan

Each is a pragmatic choice with the plan's intent, recorded where it was made.

1. **The framework's shape** differs from the PLAN 4.5.2 sketch in the places listed in
   `framework.md`, "Differences from PLAN 4.5": no `reserve` hook (ADR 0015's leases size the
   workspaces), no `translate` hook yet (no 0.1 user; `hyper_sssp` and `mosp` bring it), `prepare`
   reads the old view, a `normalize` hook, `finalize` takes the stats, `count` is overloaded on the
   view type, the static Tier B hook is `compute_fused`, lifecycle members carry the validation of
   PLAN 4.8, and `run_update` keeps the type-erased participants of M1a with a typed adapter on
   top. File names follow the task (`views.hpp`, `budgets.hpp`).
2. **Temporary migration switches.** Both migrations used a per-backend switch between the old
   participant and the new problem for their first two commits (the backend is only known in
   `before_apply`); each was removed in the CUDA commit.
3. **Stage rows.** Under set semantics `cycle_count.normalize` is called twice per update; on CUDA
   cycle_count's own stages sit inside a new `cycle_count.enact_fused` row. The gated regions read
   the same stages as before (`parity/results/M3.md` section 2.3).
4. **Errors from the fused engines** are raised through the context's device-error word and
   thrown by the enactor (the same types and messages).
5. **The "before" builds of the migration steps** were `f664f96` and `b8c3794` (each the end of
   the previous step), not `019ef13`; the final reading against `019ef13` itself is section 4.
6. **The kit** lives in `cpp/tests/conformance/` (not `cpp/tests/support/`); "the registry" is two
   generated C++ registries (the public one and the kit's), the Python one waits for M5; C4 is
   skipped; the scaffold writes graphs on the host backends only (ADR 0022).
7. **The budgets** gained reservations and container work, so that "once reserved" in I9 is
   precise (ADR 0022).
8. **The API freeze** is a committed declaration listing from the Doxygen XML, not an ABI dump
   (most of the API is templates; `abidiff` joins at 1.0, PLAN 5.9); `io/*`, `generators/*` and
   `testing/*` are tracked but frozen only in M5 (ADR 0023).
9. **Measurement.** Several refactor readings used dynG-against-dynG A/B runs
   (`--baseline-exe`) at 21-41 rounds, because the original's side was too noisy on OpenMP to
   resolve a 2 % change; the gate readings against the originals follow the approved protocol.
10. **Records.** Two CUDA JSON records of step 3 are compacted to the repository's 256 KB limit
    (the full ones are in `$DYNG_SCRATCH`); performance records made while documentation was being
    written carry `+dirty` (the binaries are those of the named commit).

## Lessons

1. **Extracting a framework from two opposite, working ports was the right order.** Every hook
   of the template has a real user, and the two families were exercised by the first two
   algorithms; nothing in the framework is speculative. The rule of two kept `cpp/src/operators/`
   empty for now, which is honest: the two algorithms share the pipeline, not their loops.
2. **Name the stages first, then move the code.** Pinning each algorithm's stage sequence in a
   test before its migration (`TheEnactorsOpenTheStagesOfTheTimedRegions`) made "the timed
   regions are unchanged" a checked property instead of a claim.
3. **dynG against dynG is the refactor's measurement.** Against the original, the OpenMP side
   moves by up to 24 % between rounds; against the previous dynG build in the same session the
   noise mostly cancels. The harness option (`--baseline-exe`) paid for itself in the first
   migration.
4. **Short OpenMP batches are bimodal per process.** Every local10k run of both builds, and of
   the original, lands in one of two modes 8-10 % apart, chosen when the process starts; a median
   over 21 or 41 rounds follows the mode mix, which changes between sessions of the same binaries.
   Reading a 2 % refactor bar on such regions needs a mode-aware comparison (split at the gap,
   compare mode by mode), which M3 did by hand; the harness should report it (open item 9).
5. **Code placement is a real effect on this CPU.** Unchanged code (the CSR text reader,
   `graph.build`) moved by 5-20 % between builds when unrelated code grew, and padding branches
   off 32-byte boundaries (`-Wa,-mbranches-within-32B-boundaries`, the Cascade Lake
   jump-conditional-code erratum) removed the difference every time. A 2 % refactor bar on
   end-to-end regions cannot be read on such a machine without controlling layout; the gates
   against the originals (5-10 % bars) are not affected in practice. Whether the parity preset
   should pad branches is a protocol question for the author (open item 1).
6. **The conformance kit found real problems on its first run** (a heap allocation per gather in
   the OpenMP sssp engine, and a charge of the graph's own upload to cycle_count's budget), which
   the ports' own suites could not see. Generic checks across algorithms are worth their cost.
7. **An API freeze needs a mechanical check**, or it is only a statement. The listing is cheap
   (it reuses the Doxygen XML) and shows the API diff next to the code in every pull request.

## Open items

For **the author**:

1. **Layout control in the parity preset.** The end-to-end readings of the host engines (and
   single update regions near the 2 % bar) move with code placement on the Xeon Gold 6258R
   (sections 1.4, 2.4, 3.3 and 4 of `parity/results/M3.md`). Options: (a) accept, and read
   refactors dynG-against-dynG on the gated update regions only, as M3 did; (b) add
   `-Wa,-mbranches-within-32B-boundaries` (or `-falign-jumps=32`) to the `parity` preset for both
   the originals and dynG, which changes the measurement protocol of ADRs 0018/0021 and needs the
   author's decision. The recommendation is (a) for 0.1 and a measured proposal for (b) before the
   0.2 gates.
2. The API review (ADR 0023) was accepted under delegation; the author may want to read its
   findings table and the sketches before M5 binds the API to Python.

For **the review of M3, M5 and later**:

3. C4 (fused equals operators) waits for a backend with two engines (the sssp operators engine,
   M7).
4. The scaffold writes no CUDA backend and no hypergraph container (0.2).
5. `profiler` moves behind a pimpl before 1.0 (ADR 0023, finding 10); `io/*`, `generators/*`,
   `testing/*` are reviewed and frozen in M5; the Python binding notes of ADR 0023.
6. The `api-check.yml` workflow (the `api-change` label check and `griffe`) in M5; until then the
   reviewers check the label by hand when the baseline changes.
7. The CI job and CTest of the scaffold need network access for GoogleTest when the CPM cache is
   cold.
8. The reference builds of this milestone under `$DYNG_SCRATCH` (`m3-final/`: `019ef13`,
   `47c9e18` and the two padded builds, about 90 MB) are kept for the review and deleted after it;
   the earlier `m3-sssp/base` and `m3-cycle/base` were deleted in step 5.
9. The OpenMP sssp local10k batches are bimodal per process (`parity/results/M3.md` section 4.2).
   `parity/perf_ab.py` should detect a bimodal region and report the mode-by-mode ratios next to
   the median, so that a refactor reading does not depend on the mode mix of one session.
10. The migrations cost 0-2 % within a mode on the short OpenMP sssp batches (7-10 ms updates;
    none on the 50K batches or on CUDA): the enactor's per-update bookkeeping. Within the bar; worth
    a profile when the operators engine (M7) touches the same path.

## Re-estimate of the roadmap

**Measured.** M3 was estimated at 2-4 days of focused work (the M2b retrospective) and took one
long day of wall-clock time for its five steps (about 8.5 hours for steps 1-4 by the commit
times, and about half a day for step 5, most of it the gate suites: sssp 4 graphs x 3 batches on
two backends against the originals and against `019ef13`, and cycle_count's M2a and M2b case lists
on two backends, about four to five hours of exclusive lock time). As in M1-M2 the independent
review is still to come and has found real defects every time (about half a day of fixes).

**What this changes.** The framework and the kit make the next ports more mechanical (a port is
now a problem class plus traits, checked by C1-C12 from day one), but M5 is not a port: it is
packaging (nanobind, scikit-build-core, stubs, the first TestPyPI release candidate), where the
unknowns are in tools, not in the library.
