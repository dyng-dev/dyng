### Investigation (a): the cycle_count update of the CUDA 13.4 cu13 wheel

M6a's informational wheel-vs-parity row (open item 4 of its retrospective) read the DD k = 4
update (25K + 25K) of the cu13 wheel built with the pinned CUDA 13.4 at 1.088x the parity build
(CUDA 13.1), while the wheel built with 13.1 read 0.988x.

**The kernels are the same.** The update kernels of the parity overlays built with 13.1 and 13.4
(`parity/wheel_vs_parity.py build-parity`, the same commit, sm_86, the same GCC 12.2 host
compiler):

- SASS (`cuobjdump -sass`, per kernel): `count_owned_cycles_kernel<4, unsigned>`, the kernel of
  this update, has the same 560 instructions and 20 registers instead of 22; the other
  `count_owned_cycles_kernel` widths differ by -64 to +8 instructions (fewer moves and IMADs under
  13.4); `item_counts_kernel` and `mark_owners_kernel` are identical.
- Nsight Compute 2025.4.1 (GPU 0, `--clock-control base`, the kernels inside the NVTX range
  `cycle_count.update`, 6 updates per side): the kernel time per update is 689.2 us (parity 13.1),
  687.0 us (parity 13.4), 691.7 us (wheel 13.1) and 686.2 us (wheel 13.4). 13.4 is 0.3-0.8 %
  *faster*; `build_next_rows_kernel` (224 us) and `count_owned_cycles_kernel<4>` (2 x 180-183 us)
  dominate, and the CUB scan kernels of the newer CCCL have other policy names and 48 -> 58 registers but the same time.

**The difference was a process mode of a host stage.** About 70 % of the update is
`cycle_count.normalize`, the framework's normalization of the batch on the host (ADR 0020); it is
compiled by the host compiler, not by nvcc. `wheel_vs_parity.py` keeps one long-lived process per
side, so a side reads one process (one heap layout and process mode, `parity/results/M3.md`
section 6.3) for a whole session. The attempt before the interruption read the update side by
side in such sessions (GPU 0 and, while GPU 0 had a foreign job, GPU 1; the GPU 1 readings are
informational only): the *same* build against itself read 3.73 against 6.39 ms (13.4 vs 13.4,
GPU 0) and 4.01 against 5.73 ms (13.1 vs 13.1, GPU 1), and 13.4 against 13.1 read anywhere from
0.81x to 1.60x depending on the session. The final reading therefore runs every side in 8
separate processes (15 rounds each after a warm-up, the side order rotating, GPU 0, the exclusive
lock, the boost clock lock; `final_a.py`, record in `parity/results/R020-investigations.json`):

| Stage (device ms, median over 8 processes [min-max]) | parity 13.1 | parity 13.4 | wheel 13.1 | wheel 13.4 |
|---|---|---|---|---|
| `cycle_count.normalize` (host) | 2.209 [2.165-2.237] | 2.103 [2.072-2.125] | 2.151 [2.100-2.189] | 2.126 [2.116-2.155] |
| `cycle_count.count_minus` | 0.279 | 0.278 | 0.281 | 0.279 |
| `cycle_count.commit` (`graph.apply` 0.287-0.289) | 0.299 | 0.300 | 0.297 | 0.296 |
| `cycle_count.enact_fused` (`count_plus` 0.210-0.215) | 0.240 | 0.237 | 0.238 | 0.233 |
| **`cycle_count.update`** | **3.118** [3.085-3.156] | **3.010** [2.965-3.037] | **3.025** [2.961-3.055] | **2.984** [2.960-3.016] |

13.4 / 13.1: 0.965 for the parity builds, 0.986 for the wheels; every device stage is within
1.5 % (13.4 slightly faster), and the spread is in the host stage. (The wheels are M6a's,
`476ab72`; since then the cycle_count sources changed only in one error message.)

**Recommendation.** Keep CUDA 13.4 for the cu13 wheel: there is no 13.4 slowdown to fix, so no
library change and no ADR. A future wheel-vs-parity row of a short, host-heavy update should be
read over several processes per side, as here, not from one long-lived worker per side (a note for
`parity/wheel_vs_parity.py`; the row is informational, PLAN 7.7, and no gate reads it).

### Investigation (b): layout control for the 0.2 gates (a measured proposal)

The open decision "Layout control for the 0.2 gates" (GOVERNANCE.md; `parity/results/M3.md`
sections 5.4 and 6.3) asks whether the gates against the originals should control code placement.
Measured on a representative subset of the gate readings, at the release library code (sources of
`1474a92` = the release commits'), GPU 0 / the Xeon, the exclusive lock, the contamination monitor
(at most 1 round repeated per reading), outputs byte-identical / histograms equal to the goldens in
every reading. Variants of the host code, built from the `parity` / `parity-cuda` presets with:
**L0** no flag (the accepted presets); **F** `-falign-functions=64`; **FB** F plus
`-falign-loops=32` and the assembler's `-mbranches-within-32B-boundaries` (the mitigation of the
Skylake-derived cores' jump-conditional-code erratum). "A" is the original: A0 the unpatched build
of the harness, AF / AFB the same unpatched sources rebuilt with the same flags in a separate work

heap layouts, ADR 0024). Ratios dynG / original (or variant / L0), medians:

(Compact records in `parity/results/R020-investigations.json`; the full records in
`$DYNG_SCRATCH/r020/inv-b/records-final`.)

What the readings say:

1. **dynG against dynG, F changes nothing beyond noise**: every region of B0-BF is within
   0.974-1.019 (ADR 0024's reading over heap layouts). Function alignment alone is not a speed-up;
   it would only fix *where* the hot functions fall.
2. **FB is a real speed-up of dynG's text I/O**: dynG's sssp end to end is 0.79-0.81x of L0 in
   every round (21 / 21, unimodal; the compute regions within 0.976-1.024), and the cycle_count
   OpenMP update is 0.90x. The branch-boundary mitigation helps the branchy readers and loops on
   this Cascade Lake CPU.
3. **The gate ratios move with the originals' layout as much as with dynG's**: rebuilding the
   *original* with F moves the roadNet-CA local10k per-objective ratios from 0.73-0.85 (A0-B0) to
   0.61-0.66 (AF-BF), i.e. the original's short updates got 15-25 % slower from its own placement.
   Controlling only dynG's layout (A0-BF) moves the ratios by up to 0.06 either way; controlling
   both sides is a change to the originals' build, which the parity rules pin (unpatched, as the
   original's build files build it).
4. **Every gated reading passes in every variant with a wide margin**: the largest gated ratio in
   the table is 0.969 (cycle_count CUDA end to end, gate 1.10) and the largest per-objective one
   0.933 (gate 1.05). Layout control is not needed for the 0.2 gates to hold, and no variant comes
   near a gate.

**The proposal for the author** (attached to the open decision; the decision stays open and
criterion 3's gates use the accepted one-layout protocol of ADRs 0018 / 0021):

- *For the gates against the originals:* keep the one-layout protocol (the default), with the
  originals built exactly as their build files build them. Reason: reading 3; a flag in the parity
  presets alone would shift the ratios by about as much as the noise it is meant to remove, and
  aligning the originals changes the pinned baselines. The layout spread (about ±0.06 on the short
  OpenMP sssp updates, ±0.02 elsewhere) is the known uncertainty of a single reading and is far
  inside every gate (reading 4).
- *For dynG-against-dynG bars (refactors):* keep ADR 0024 (reading over heap layouts and modes).
- *Separately, as a performance option for the release builds (not a protocol change):* FB in
  the release presets and the wheels would make dynG's end-to-end runs about 20 % faster on this
  CPU family with no regression elsewhere; it needs its own ADR, a parity run of the release
  builds, a check with the wheels' toolchain (gcc-toolset 14 in manylinux_2_28) and a reading on a
  CPU without the erratum. Recommended for 0.3, not 0.2.0 (it would change the measured library
  after the certificate's protocol was fixed).

### Deviations and decisions (each with the same intent)

1. **(a) is read over processes, not with the M6a harness.** The M6a row's tool reads one
   long-lived process per side; its result for the DD update depends on the process mode of a host
   stage (above), so the final reading uses 8 processes per side with the same batch, plus Nsight
   Compute on the kernels. The harness itself is unchanged.
2. **(b)'s aligned originals** are rebuilt from the unpatched sources in a separate work area
   (`$DYNG_SCRATCH/r020/inv-b/scratch-F`, `scratch-FB`), never in `$DYNG_SCRATCH/ref`, so no gate
   reference changed.
3. **No library change** came out of either investigation, so the certificate measures the
   release code as committed here.
4. **The GPU 1 readings of the interrupted attempt** are kept only as the evidence of the
   process-mode spread, labelled informational; every reading of the tables above is on GPU 0.

### The end-to-end slowdown since 0.1.0 (finding 12)

**Attribution.** A dynG-against-dynG stage A/B (the dyng-compat-mosp report lines and profiler
stages of 0.1.0's `d13d393` against `5a6cd66`, sssp OpenMP 28 threads, safe50k, 11 alternated runs

The reviewer suspected `0b388f7` (M6b's bounded reservations: `read_values` counts the line
breaks of the whole Values file). That count runs only on the strict path, which re-reads a file
after an error: the concurrent pass, the only one a valid graph takes, already counted them in
0.1.0 (its `m` is unknown there). The success path of the reader is the same source in 0.1.0 and
here (`git diff d13d393 -- cpp/src/io/csr_triplet.cpp cpp/src/util` touches only the strict
path), so the 18 % was, most likely, code placement: the text reader's hot loop moved with the library around it (the
layout sensitivity of the text readers that investigation (b) measured, about 20 % from function
and branch alignment on this CPU, which has the JCC erratum). Reading the three files alone (a

is the critical one of the three concurrent reads (about 525 of the 530 ms on rgg).

**The fix (`b1a4869`).** `text_scanner::next_number()` / `next_number_in_line()` scan a token and,
when it is 1 to 18 decimal digits, return its value on the way, so its characters are read once;

digits, anything else) through `parse_integer()`, so values, error messages and locations are
exactly the general path's (pinned by `TextScanner.NumbersMatchTheGeneralPath` over the token
classes and three ranges). `read_values()` writes each weight straight into its objective's
column once the columns exist, instead of through a per-line vector. Nothing of the fuzz guards
changed: the reservations stay bounded by what the file can hold (`0b388f7`), the strict re-read
on any error is the same, the corpus and regression replays pass (`ctest -L fuzz`, 14 tests), and
`ci/fuzz.sh --time 120 csr_triplet` ran 37,318 inputs without a finding. Matrix Market, the batch
and result readers keep the general path (they are not on a gated path; the edge-list reader of
cycle_count has its own parser, unchanged since 0.1.0, whose `static_read` moved -2 % to +4.5 %
between the two certificates).
