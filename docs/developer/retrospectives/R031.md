# Retrospective: R031 (the final-release pull request for 0.3.0)

Status: **in progress** on the branch `release-0.3.0-final` (from `main` at `20bc2d0`, the merge
of pull request #18 with R030; the signed tag `v0.3.0rc1` points there). Release 0.3.0 is M8 +
M9 (PLAN Appendix F); its release candidate 0.3.0rc1 is on TestPyPI since 2026-10-28 (`dyng`,
sdist and wheel, `dyng-cu12` and `dyng-cu13`, `release.yml` run 40606434243). R031 smoke-tests
that release candidate from TestPyPI (`docs/developer/release.md` step 8), makes the
final-release pull request (step 9: the version, the CHANGELOG, `CITATION.cff`, the status texts,
the approvals log) and carries the release candidate's certificate over to
`benchmarks/results/0.3.0/`. Nothing is published by this milestone: the orchestrator pushes the
branch; the author merges the pull request; the AI assistant pushes the signed tag `v0.3.0` and
creates the GitHub Release on the author's behalf (GOVERNANCE.md, 2026-10-22); the author
approves the PyPI deployments `pypi-cu12` and `pypi-cu13` (one dialog), then `pypi`. The planned
tag day is **2026-10-29** (UTC).

## Step 1: the smoke test of 0.3.0rc1 from TestPyPI (rc-smoke)

**Result: passed, everywhere; nothing to fix.** No defect of the code or of the documentation
was found, so the library and the release candidate's documents are unchanged by this step and
the certificate can still be carried over (step 9 of `release.md`). The only commit of this step
adds this section and the log `benchmarks/results/0.3.0/checks/smoke-rc1.txt`.

hypergraph, `triad_count`, its CLI command and its example) after the upload, in its five parts
(`cpu`, `plugin cu12`, `plugin cu13`, `extras cu12`, `extras cu13`), on 2026-10-28 between

### What it means for the release

- Acceptance criterion 1 is met: no blocker for the final release from the release candidate.
- No code, test or user-facing document changed in this step: only this page (in the `repo`
  scope of `parity/certify.py` alone, whose checks the final-release pull request runs again on
  the final tree anyway) and the new `benchmarks/results/0.3.0/checks/smoke-rc1.txt` (outside
  every scope). The `library`, `tests` and `packaging` scopes are those of 0.3.0rc1's measured
  commits, so the certificate can be carried over (release.md step 9). The directory `benchmarks/results/0.3.0/`
  exists from this step with `checks/smoke-rc1.txt` only: the carry-over copies the release
  candidate's **contents** into it (`cp -r benchmarks/results/0.3.0rc1/. benchmarks/results/0.3.0/`;
  release.md's `cp -r benchmarks/results/X.Y.ZrcN benchmarks/results/X.Y.Z` would now create
  `0.3.0/0.3.0rc1/`), and the certificate's `README.md` gets this smoke test's summary.
- `release.md` step 8 names "a CPU machine and the GPU machine". As for 0.1.0 (R011) and 0.2.0
  (R021), only the GPU machine is available to this milestone; the CPU package's host backends
  ran on it, and the plugins' behaviour on a machine without a GPU or a driver was checked with
  the two fallbacks above (`CUDA_VISIBLE_DEVICES=` and `ci/without_cuda_driver.sh`); the hosted
  runners of the release run checked the plugins' install without a GPU too (its "Plugin cuN
  install test, no GPU" jobs, green).
