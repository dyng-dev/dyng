### A CUDA test case `pytest -m gpu` did not select (fixed in this branch)

The CPU suite skips 90 test cases for want of CUDA, while `pytest -m gpu` selects 89 (81 passed
and 8 skipped, 845 deselected out of 934). The 90th is `test_examples.py::
test_hyper_sssp_prints_the_expected_distances[cuda]`. It was parametrized with a bare `"cuda"`
and an inline `pytest.skip`, instead of the module's `_CUDA` parameter, which carries the `gpu`
marker and the skip condition. So `pytest -m gpu` deselected it. The GPU tests of the plugin
wheels (`ci/plugin_wheels.sh`, release.md steps 8 and 10) therefore never ran the hyper_sssp
Python example on CUDA. It could run only in a full pytest run with a CUDA module active, which
none of the release's scripts makes (`ci/python.sh` tests the editable CPU install).

This is a defect of the test suite, not of the library or the wheels. The same example data on
CUDA are covered by the C++ example's CTest `example.hyper_sssp_update.cuda` (same expected
bytes), and the Python API's hyper_sssp on CUDA by `plugin_smoke.py` and `test_hyper_sssp_cuda.py`.
Run on the published wheels in the four plugin venvs
(`CUDA_VISIBLE_DEVICES=1 DYNG_REQUIRE_CUDA=1 pytest -v python/tests/test_examples.py -k
hyper_sssp_prints`, from the tag's tree; `hyper-sssp-example-cuda.log`), it passed everywhere:
both `[sequential]` and `[cuda]` PASSED with cu12 and with cu13, on 3.12 and on 3.13.

The fix (`184042a4`) uses `_CUDA` for the test. It also adds `python/tests/test_gpu_marker.py`,
which fails when any test case of the session parametrized with `backend="cuda"` lacks the
`gpu` marker (it failed on the old `test_examples.py`), with a unit test of the check itself.
With the fix, `pytest -m gpu` in the cu13 / 3.12 venv of the published wheels gives 82 passed and
8 skipped. The CPU suite against the published CPU wheel gives 837 passed and 99 skipped: the two
new tests, the same skips. At the final tag, step 10's GPU tests run 82 cases per venv instead of
81.

The change is in `python/tests` only, which is in the `packaging` scope of `parity/certify.py`.
Of the narrower scopes, `library` and `tests` (`cpp/tests`, `cpp/fuzz`, `examples`, `README.md`),
the fix touches neither. So it does not stop the carry-over: the `packaging` checks (the
distributions with their wheel tests and the GPU tests of both plugins) run again on the final
tree, as step 9 requires anyway.
