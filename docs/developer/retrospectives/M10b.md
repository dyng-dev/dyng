### Deviations from the plan and the step's text (each with the same intent)

1. **The operators stay in the algorithm's folder** (`algorithms/label_propagation/operators/`,
   namespace `lp_ops`), not in `cpp/src/operators/` as PLAN 11.4's M10 row lists them: PLAN
   4.5.3's rule of two (one user each); ADR 0102 records the promotion rule.
2. **The operators take the resources and name their executor** (`neighbor_reduce<cuda_exec>(res,
   ...)`), not an executor object: an operator with its own kernels needs the stream, which
   `operators::cuda_exec` keeps private, and M10 does not change `cpp/src/operators/` (the shared
   headers; `execution.hpp` is M11's carried item).
3. **No operators twin of `schedule::in_place`** (PLAN 4.5.4 and the step's text: optional):
   compute() and update() with `engine::operators` under `in_place` raise `not_supported_error`
   (the first GPU ctest found the kit's C8 building an in_place chain on the operators engine that
   compute() accepted; compute() refuses it since). So the in_place
   mutant (`inplace_plain_jacobi`) has nothing to act on in the operators engine; the five other
   mutants fail its own cases (the CTests `label_propagation.mutation.cuda_operators.*`), and the
   in_place mutant keeps its fused and host rows.
4. **compute() is IrLP on every engine** (the published baseline, PLAN 6.4.7: "IrLP stays
   deliberately unchanged"); `engine::operators` no longer raises in compute() under `damped`.
5. **One kernel per phase, and the arithmetic of the fused engine**: the large bin's block is
   1024 threads while the frontier holds at most 1024 vertices (the fused engine's persistent
   kernel takes those iterations) and 256 above, so the labels are the fused engine's bits; the
   persistent kernel itself has no operators twin.
6. **The calibration builds the compatibility tools' algorithms only** (DYNG_ALGORITHMS =
   label_propagation, sssp, cycle_count, mosp, triad_count; a reconfigure per variant recompiles
   label_propagation's CUDA sources alone); the control variant proves the build reproduces the
   goldens' bits.
7. **The stage trace** records the fused engine only (the operators engine's parity is its bits
   and counts).

### Deviations from the plan and the step's text (each with the same intent)

1. **No `graph_view::row_start`** (ADR 0069 section 8 planned one): `out.row_ptr[v]` is row v's
   start for slotted and slack rows, so the engines read both through `(row_ptr[v], row_end[v])`
   and share their kernels; `out.row_ptr` of slack rows is not monotone (documented in
   `graph_view.hpp`; ADR 0103 point 1). No new public name.
2. **M11a's slack-row accessor is not reused** (ADR 0103 point 13): `hyper::slack_row_view`
   describes a `slack_csr` line graph's node rows (unordered sets, a weight per node); graph rows
   need a weight per entry, vertex states and the entry order a move keeps. Its file comment
   ("label_propagation reuses it in M10b") is M11's text, left to M11.
3. **`update()` refuses vertex growth** on slack rows (a result keeps one label per vertex of its
   graph); `with_capacity()`'s `vertex_capacity` is the stream's final vertex count. Vertex growth
   itself is the container's and is tested there.
4. **The streaming threshold on CUDA walks the deleted rows on the host** (a download of the rows
   of G_t per update in the streaming mode only; ADR 0104's alternative "a device kernel" is
   deferred: no gate, AD16).
5. **The forced compaction is internal** (`detail::graph_access::compact_slack`, for the tests);
   no public compaction call or tunable bound (no new public name).
6. **The kit's slack preset builds with half of the capacities** so that rows move in every check
   (C7's row overflow becomes a move on slack rows); the full-capacity case is the slack suite's.
7. **The checker's oracles on slack rows** run in the slack suite (`Streaming*`: the same oracles
   as `label_propagation_checker_test.cpp`, the rows against the kit's slack model instead of the
   slotted rows' exact slot order, which a move changes by design).
8. **The stable algorithms are not re-read in this step** (the step: "re-read them only if code
   they compile changed; state the diff either way"). The diff: the branch changes code every
   algorithm compiles: `apply_summary` gains two `int64` fields (copied into every `stats::batch`),
   `normalized_batch` a vector and a flag, `graph.cpp`'s dispatch the slack branches; the compact
   rows' apply, the device merge and every algorithm's own code are unchanged. The re-read under
   ADR 0024 is taken once, on the final library, in step 4's final re-read (criterion 12), which
   also covers the module-loading change the author's decision of 2026-11-05 assigns to M10b
   (taking it twice would spend about a day of the shared exclusive calendar on a library that
   step 3 changes again). Nothing is relaxed: the step-4 reading is the gate.
9. **The readings use the compatibility tools' build** (`DYNG_ALGORITHMS = label_propagation,
   sssp, cycle_count, mosp, triad_count`, as step 1's calibration) on both sides of every
   dynG-against-dynG reading (A and this step's library from `git archive`, built the same way).
10. **The memory report (slack against slotted) ran in a GPU-1 quiet window** although it is
    reported, not gated, so that no foreign process contaminates it.
11. **The Python batch readers refuse what they cannot carry yet.** The C++ readers now accept
    the vertex operations, vertex records and float32 weights of AD13; the Python batches carry
    neither (step 3's work), so `dyng.io.read_batches` and `dyng.io.BatchReader` raise
    `NotSupportedError` naming them rather than return the batches without them (a silent drop
    the final checks exposed); `write_batches` writes a batch's vertex operations, as the C++
    writer does.

### Lessons for M10 as a whole

- **Run every lint of the CUDA branch before the final readings.** `ci/check.sh`'s clang-tidy
  compiles the CPU branch only; `ci/gpu_local.sh`'s, which compiles the CUDA branch, found the
  kernel groups' registration declarations after the whole certificate set had been read, and the
  comment-only fix forced the set again (about 5 h of machine time), because certify compares
  sources, not binaries.

- **A reading's commit must be clean, and the drivers must enforce it.** A documentation edit left
  uncommitted for a few hours made a whole night of readings uncertifiable (`+dirty`); the second
  set took another 10 h of machine time. The drivers now wait for `git status --porcelain` to be
  empty before every job; records are drafted outside the worktree and committed in one step at
  the end.
- **A change that only moves the load time of code can still change performance**, twice in this
  milestone: the kernel groups first deferred label_propagation's module loading into its first
  timed update (two misses), then, with every group lazy, shifted the device memory layout enough
  to slow sssp's persistent kernel by 4 % on one graph. Only the full gate and ADR 0024 sets found
  them: a quick A/B of the changed algorithm alone (the LP slotted path) would have passed.
- **The ADR 0024 set against the right base.** Against `b2b1524` the set mixes M10a's, M11's and
  M10b's changes; against `ae5fc47` (main before M10b) it reads M10b's own change and confirms
  the author's regions separately. With two tracks merging into one release, each milestone's
  final dynG-against-dynG reading should name the base that isolates its own change.
- **Interleaving exclusive windows with shared-lock work wastes GPU time.** `flock` gives no
  priority to a waiting exclusive lock, so a CPU check suite of two hours delayed every gate
  window behind it; the `polite()` yield of the GPU-1 driver helped, the CPU checks had none.
- **The in_place schedule's tail** (five recorded misses in M10, the last in this step's
  pre-merge reading, decided by the author each time) did not recur in the final cloud on the
  merged library: every run of I inside the frozen envelope, in the replays and in
  `ci/gpu_local.sh`'s label_propagation step.
- **Integration owes readings, not only merges**: M11's gates read against the original on a
  different evening can move by a few percent through the original alone (the ia3_hsosp
  first-batch row: 0.992 in M11b, 1.065 / 1.050 / 1.042 in this step's three readings); the
  release reading R040 should expect it.

### Lessons

- **A tail event of probability about 1/15 per run gets hit by one of three runs in roughly one
  reading of five**, and a certificate needs several readings per milestone (the replay, the
  gpu_local step, each re-read after a code change). M10 now has eight readings of the in_place
  cloud with a run outside (the five before this round, each decided by the author, and this
  round's three). The author's rate rule of 2026-11-18 (ADR 0111) ends the cycle for the
  certificate: it judges the port's rate against the original's own rate in the same session (the
  original crossed the envelope in 3 of 30 runs at 50k in the rule's reading, twice within the
  hour). A threshold calibrated on a distribution needs a rule for its tails from the start; the
  calibration of AD5 had none.
- **A review's fixes outside the timed region still force the whole certificate set**, because
  certify compares sources: here 2.1 h of exclusive windows and about 12 h of GPU-1 time for
  fixes of the generator, the label writer and slack rows.
