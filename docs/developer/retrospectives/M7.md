### Results

- Conformance check C4 runs for `sssp` on CUDA (it was skipped everywhere in 0.1) and passes for
  the three graph types; the kit's C4 now compares after `compute()` and three batches for every
  preset, the small and medium sizes and every batch mix.
- The golden corpus: 495/495 byte-identical with the operators engine, with 32- and 64-bit edge
  offsets (`parity/results/M7.md` section 1).
- The randomized suites in the CUDA executable compare the operators engine with the fused engine
  and with the host backends on every chain (trees, `invalidated`, `affected`, `packed_parents`);
  the MOSP fixtures, the packing boundary, the distance-only fallback, the input checks (an
  out-of-range distance, a parent cycle), the steady-state allocations and the strict budget run
  on both engines.
- Speed against the fused engine (`parity/results/M7.md` section 2; informational, no gate):
  1.03-1.18x on the 50K batches of the four gate graphs, 1.10-1.62x on the local 10K batches,
  whose many short near-far rounds each cost a host round trip of about 8-9 us.

### Deviations and decisions (with reasons)

1. **MOSP_ESCHER's structure, MOSP-CUDA's semantics.** PLAN 6.4.2 names MP1 as the structure to
   follow. MP1 is an earlier state of the algorithm and differs from MOSP-CUDA@e220ee2 in details
   that change outputs or error reports (no parent-cycle detection, candidates above the bound
   packed, no distance-only fallback, no `affected`). The engine keeps MP1's shape and takes every
   detail from the fused kernel, so the bytes are the same (ADR 0026 items 1 and 3).
2. **Fewer host round trips than MP1.** MP1 synchronizes after Step 1, after the pull, twice per
   threshold raise and once per push iteration. Here the pointer-jumping rounds end on the device
   (a round after a converged one returns at once), the frontier's length and the threshold stay
   on the device, so an update synchronizes 3 + iterations + epochs times. That is the engine's I9
   budget, stated after the phase.
3. **Grid-stride kernels** with at most as many blocks as the device holds at once (MP1 launches
   one thread per item). The pointer-jumping rounds that have nothing left to do then cost one
   empty launch of a few hundred blocks instead of n / 256 blocks.
4. **Rule of two.** Nothing enters `cpp/src/operators`: `cycle_count`'s CUDA code shares none of
   these operators (it uses work counters and CUB scans), and the planned second user of
   `invalidate_subtree` and the pull is `hyper_sssp` (0.3). The shared device blocks of the two sssp
   engines live in the sssp folder (`kernels.cuh`). PLAN 4.5.3's `schedule`, `sync_rule` and
   `tie_break` policies were not needed (one schedule; the tie rule is the packed minimum).
5. **CHANGELOG placement.** The M7 entries are a block at the end of `[Unreleased]` (before
   `[0.0.1]`), so the release-prep pull request on `main`, which rewrites the head of
   `[Unreleased]`, does not touch the same lines; after 0.1.0 the block stays under
   `[Unreleased]`.

### Open items

- The operators engine's speed on updates with many short near-far rounds (1.4-1.6x the fused
  engine on the local batches). It is the fallback, not the default, and has no gate; if it ever
  matters, several rounds per synchronization (or a CUDA graph of the rounds) would remove most of
  the round trips. `docs/developer/plan.md`'s 0.2 estimate of "within 1.05x of the fused one" is
  met only on rgg; the author may want to confirm that it was an estimate, not a requirement.

### Notes for the next steps

- `mosp` composes K `sssp` problems: the engine choice is `sssp::options::cuda_engine` of each
  objective (the sketch's `mosp::options::engine` passes it through). The operators engine shares
  the pooled `sssp_cuda_workspace` (its control block is sized for either engine).
- `dyng-compat-mosp` already sums whichever engine's stages ran for the per-objective SOSP region,
  so a `mosp` driver can reuse that rule.

### Results

- The golden corpus with the whole MOSP update (`--mosp`): 495/495 byte-identical on sequential,
  OpenMP with 1, 4 and 16 threads, and on cuda with the fused and the operators engine with 32-
  and 64-bit edge offsets, for the K updated trees, the updated CSR, the `invalidated` counters
  and, new, `combined/{distancesCsr,SSSPTreeCsr,mospCosts}.txt` (K from 1 to 5 and 32 in the
  corpus). Records `M7-mosp-goldens-host.json`, `M7-mosp-goldens-cuda.json`.
- Preference vectors: the 8 committed cases (the thesis example with Pref {4, 1, 4} and
  {4, 4, 1}, K = 2..4 with preferences, `-k 2` on a 4-column graph) byte-identical on every
  backend; both originals agreed on them first. The thesis' costs (15, 3, 20) and (15, 24, 7)
  are asserted by the hand tests on every backend. At scale: roadNet-CA (K = 3, Pref {4, 1, 4},
  the 50K and the local 10K batches) byte-identical to MOSP-OpenMP's `mosp` on the OpenMP
  backend, and to MOSP-CUDA's on cuda (section 3).
- The conformance kit: C1-C12 for `mosp` on every backend and graph type (C4 compares the fused
  and the operators engine through the K updates and the combined solve; C8's budget on cuda is
  K + 3 synchronizations; C10 pairs mosp with sssp and cycle_count); sssp's and cycle_count's
  suites still pass with mosp as a C10 partner on 3-column graphs.
- `ctest -L cpu` (dev): 694/694; `ctest -L gpu` (dev-cuda, GPU 1): 321/321;
  compute-sanitizer memcheck, synccheck and racecheck on the mosp CUDA suites: 0 errors.
- Portability: the Clang 18 syntax pass (171 files, 0 failures) and the fortified cpu-only
  Release build are clean; `ci/docs.sh` passes (670 declarations in the API baseline);
  `ci/scaffold_check.sh` passes (the kit's changes keep the scaffold green).

### Deviations and decisions (with reasons)

1. **mosp_problem is a participant, not a framework problem.** PLAN 4.5.2 calls mosp "plain C++
   composition"; the framework has no composite problem type and mosp is its first user (rule of
   two). `detail::mosp_problem` implements `update_participant` and owns K
   `problem_participant<sssp_problem>`: one commit for the K objectives, each objective through
   its own update enactor (stages nested in `mosp.objective`), then the finalize step. It
   composes with any result in `dyng::update()` (C10).
2. **The combined solve on a view.** The combined CSR is pooled scratch, not a `dyng::graph`
   (sketch question 3), so sssp got `sssp_solve_view()`: the static enactor with the backend's
   engine on a raw view, into caller-owned arrays. The sequential engine's distance-only parent
   recovery reads in-edges (the OpenMP and CUDA engines read out-edges there), so the sequential
   combine builds the combined graph's in-edge CSR when the packing does not fit; tested with
   L = 2^20 on 2^21 vertices.
3. **API additions to the sketch** (ADR 0027): `options::num_objectives` (MOSP's `-k`); `delta`
   applies to the K updates only (the originals solve the combined graph with its own automatic
   width); the path costs cover the K objectives and are host memory on every backend (the
   compat driver writes the original's every-column file with `-k`); `affected` counts the
   vertices whose combined distance or MOSP parent changed (a second pair of combined arrays,
   swapped); `max_objectives` is 64 (the originals stop at 32: one byte per insertion and
   objective in the commit's classification).
4. **sssp accepts batches without insertions of any weight count** (as `graph::apply()`): the
   kit's empty batches on 3-column graphs and mosp's objectives need it. A behaviour
   relaxation of a frozen header's function, recorded in ADR 0027 and the CHANGELOG.
5. **The kit's weight columns.** `test_traits::num_weights` (default 1) gives the kit's graphs K
   columns; columns 1..K-1 are a fixed function of the edge and column 0, so the kit's generators,
   inverses (C5) and re-weightings stay unchanged; C7 checks K + 1 columns, C10 uses the larger
   count of the pair.
6. **The compat driver's default stays SOSP-only.** The sssp gates' timed regions
   (`parity/timed_regions/sssp.toml`, `perf_ab.py`) measure the SOSP part and subtract the
   original's combined step; `--mosp` is the clone of the whole `mosp` driver. With `--no-output`
   the clone does not compute the path costs, as `mosp` computes them only to write
   `mospCosts.txt` (the gate protocol runs `--no-output` on both sides).
7. **Not done in this step** (the next steps of M7): the Python binding `dyng.mosp`, the CLI
   (`dyng mosp compute|update`), the performance gates and the timed-region map of mosp. Until
   the binding exists, `python/tests/test_api_surface.py::test_uniform_contract[mosp]` fails
   (the registry lists mosp), so `ci/python.sh` is red between the steps.

### Open items

- The path costs are a sequential host pass (MOSP's `mospPathCosts`): about 0.5-1.4 s on
  roadNet-CA under the machine's load at the time (random accesses over 2M vertices). The
  originals compute them only while writing `mospCosts.txt`, concurrently with the other files;
  in dynG they are part of `update()` unless `compute_path_costs` is false. A parallel or device
  version (sketch question 1, "device later") would matter for end-to-end runs that write the
  costs.
- The timings seen while checking parity at scale were taken under the shared lock on a loaded
  machine (another user's 26-core job): not measurements. The gate step measures under the
  exclusive lock.
