Status: **ready for the release candidate** on the branch `release-0.3.0` (from `main` at
`e6f87ed`, the merge of pull request #17 with M9b). Release 0.3.0 is M8 + M9 (M8a, M8b, M9a, M9b; PLAN Appendix F); R030
makes its release candidate 0.3.0rc1: the D13 fix and the 0.3 stability records, the release
certificate on the final library code, the three distributions, and the release changes. Nothing

pull request; the AI assistant pushes the signed tag `v0.3.0rc1` and creates the GitHub Release on
the author's behalf (the author's decision of 2026-10-22, GOVERNANCE.md). Each step has its
section here; step 4 fixes the findings of the independent review of the branch and measures the
certificate again on the final library (the first certificate of step 3 is superseded); step 5,
the tag day, moves the release date to 2026-10-28, records the author's acknowledgements of
2026-10-23 and the hosted sanitizer jobs, and brings the certificate to that tree.

### Deviations (each with the same intent)

1. **The fix's form.** PLAN 4.7.3 and the D13 note ask for "catch inside the region, rethrow
   after it"; that is what `region_exceptions` does, per iteration of the two regions. A
   restructured form (one try block per thread, chunks claimed by hand) was built and measured
   (ADR 0061, "The reading") and is not faster, so the simple form stays. *(Corrected in step 4,
   ADR 0062: in the release build the restructured form is faster than the per-row form on
   sequential and slower than base on 8 threads; the per-row form stays because it is within
   0.3 % of base on both with the mitigation flags.)*
2. **Two sub-regions read above the 1.02 bar** of ADR 0024 and stay so, located, not fixed: the
   insert step on sequential (+1.5 to +4.1 ms over three batches, 0.1 % of an apply: the guard's
   small real cost) and the construction's line-graph row build (+2 to +8.5 % in the release
   build, 0.7 % with the JCC-erratum mitigation flags on both sides: code placement on this CPU).
   The regions the criterion names, apply and update, read 0.996-1.004. The construction is
   inside triad_count's CUDA end-to-end gate (on 56 host threads there), which the release
   certificate (step 2) reads again on this library. *(Step 4: ADR 0024's longer reading confirms
   both on sequential; listed for the author as open decision D14. Step 5: acknowledged by the
   author on 2026-10-23 and kept for 0.3.0.)*
3. **The update reading uses triad_count's type 1 on sequential and on coauth-DBLP** (the h_motif
   full count of coauth-DBLP takes more than ten minutes on the host, so 51 rounds were not
   possible); h_motif is read on syn1M with 8 threads. The changed code is in the apply, which
   every pattern's update runs the same way.
4. **The oracle** (`testing::triad_reference`, tracked) is outside "the container and the triad
   host engine" of the criterion; its regions had the same defect against its documented
   `std::bad_alloc`, so it is fixed with them (ADR 0061 section 2).
5. **The GOVERNANCE rows** of the author's decisions of 2026-10-22 that this step carries out
   (stability, and the D13 fix's ADR) are recorded here; the other decisions of that day (D6-D10,
   D12, the names, publishing) are the release-changes step's (criterion 5).

### Found in passing (not changed; for the author and the orchestrator)

- `sssp`'s OpenMP backend pushes into thread-local lists inside its regions
  (`cpp/src/algorithms/sssp/openmp.cpp`), which can allocate when a list grows: the same class of
  defect in a 0.1-stable algorithm, outside D13's scope (a change there needs sssp's own gates).
- `operators::openmp_exec::for_each` carries no exception out (its users, the tutorial
  algorithms, do not allocate in their functors).
- `escher::flatten_rows` runs its loop with the global OpenMP thread count, not the handle's
  (PLAN 4.7.4); it does not allocate in the region.
